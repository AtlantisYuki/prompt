# AI Agent 项目指令

## 1. 适用范围与优先级

- 默认使用中文回复，除非用户明确要求其他语言。
- 本文件定义 AI Agent（Codex、Claude Code、Grok 等）在当前仓库中的**软件开发**工具、工程和执行约束；工具专有名词按语义映射到当前 Agent 的等价能力。业务项目中本文件应位于 `.agents/AGENTS.md`。从仓库根到当前工作目录逐层读取各层 `.agents/AGENTS.md`，规则累积生效，仅在冲突时由更近层级覆盖。
- 用户要求计划、审计、解释或只读检查时，不创建文档、不修改代码、不写外部系统。
- 用户已明确调用 `sdlc-*`、要求按 SDLC 推进或已经批准施工时，不重复询问是否启动流程。
- SDLC 的阶段、模板和门禁以 Skill `$software-dev-process` 为唯一事实源，本文件不复制阶段实现细节；本文件补充软件开发场景下的工具降级、知识库、编码验证与安全边界。

## 2. 任务路由

- **Direct**：咨询、文案、单文件低风险修改、明确环境问题、局部 Bug 和低风险脚本，未显式调用专项入口时直接处理并按风险验证，不生成 SDLC 文档。
- **Standard SDLC**：多文件功能、跨模块契约、需要设计取舍或长期维护的业务逻辑，经用户确认后使用 `$software-dev-process`。
- **Rigorous SDLC**：权限安全、生产数据、数据库迁移、公共接口、不可逆操作和架构重构，必须使用 `$software-dev-process` 并保留设计决策、施工压测、回滚和验证证据。
- **Debug**：只有用户显式调用 `sdlc-debug` 时才进入；先确定授权是仅诊断还是包含修复。未显式调用的局部 Bug 走 Direct。
- **Script**：只有用户显式调用 `sdlc-script` 时才进入。未显式调用的低风险脚本走 Direct；中高风险或生产脚本先说明风险并请求用户明确进入该流程，不自动执行。

## 3. 安全与权限边界

1. 禁止读取或修改 `.env`、私钥、令牌、凭证和明确包含秘密的数据；普通 YAML、INI、CONF 按内容和任务需要正常处理。
2. 不得主动移除已有鉴权、加密、审计、数据保护或兼容措施。确需变更时说明影响，并按风险获得授权。
3. 破坏性文件操作、生产执行、数据库写入、不可逆迁移、外部发布、主分支推送和其他重大外部状态变更必须有明确授权。
4. 修改公共接口、基础组件、数据模型或扩大已批准文件范围时，先更新方案并重新评审受影响部分。
5. 遇到失败先取证并定位根因，不用兜底掩盖错误；同一路径失败后应调整假设或更换验证路径。自动排查累计失败最多 3 次，达到上限后停止自动重试，向用户说明已尝试路径、证据和阻塞并询问下一步；若提前确认需要新权限或用户决策，则立即暂停。
6. 保留并隔离无关的用户改动，不使用 `git reset --hard`、强制覆盖或大范围回滚清理工作区。
7. 用户批准进入 SDLC 时，仅授权按 Skill 维护任务文档、AI 登记和 Close 阶段的知识库同步；业务数据库写入、迁移、生产执行及其他重大外部状态变更仍需单独明确批准。

## 4. 工具能力与降级策略

只依赖当前会话实际提供的工具；下列内置工具名以常见 Agent（如 Codex）为**示意**，不绑定某一产品。Codex / Claude Code / Grok 等按**语义等价**映射后使用，例如：

- 执行命令：`shell` / `local_shell` / 终端或 Bash 类工具  
- 编辑文件：`apply_patch` / 补丁或 `search_replace` 等编辑工具  
- 计划拆解：`update_plan` / 当前会话可用的计划工具  
- 在线检索：`web_search_request` / 原生 web search 或已安装的检索 skill  

可选工具不可用时采用安全的本地等价路径，不把可选能力伪装成强制依赖，也不因可选工具缺失阻断本地工作。禁止因工具名与下表不完全一致而拒绝执行等价操作。

### 4.1 内置工具 (Built-in)

| 工具（示意名） | 作用 | 规范与使用要点 |
| :--- | :--- | :--- |
| `shell` / `local_shell` | 在沙箱内执行命令 | 默认启用。按配置执行审批策略控制交互。其他 Agent 使用其终端/Bash 等价工具。 |
| `apply_patch` | 以补丁方式批量编辑文件 | 保持 diff 清晰可审计，避免全量覆盖。编辑后自查，必要时配合 `git diff`。Grok/Claude 等使用 `search_replace` 或其他等价编辑工具即可。 |
| `update_plan` (plan tool) | 维护任务拆解与状态 | 视配置决定是否包含，使用时保持计划与实际同步，辅助复杂场景规划。复杂任务的任务拆解最终应落入设计文档或施工文档。 |
| `unified_exec` | 提供 PTY 会话运行交互式命令 | 仅在对应能力开启时使用；不可用则用普通命令执行并说明限制。 |
| `view_image` | 获取界面截图或渲染图像供分析 | 需在配置中启用图像类工具；不可用时跳过并记录未验证的视觉项。 |
| `web_search_request` | 发起在线检索以补充事实依据 | 默认可能关闭；可用时再检索。其他 Agent 使用原生 web search 或检索 skill。 |

### 4.2 外部工具 (MCP) 与降级策略

| 类别 | MCP 工具名 | 规范与降级策略 |
| :--- | :--- | :--- |
| **项目知识库 / 记忆优先检索** | `ai_localbase` | 优先使用：`knowledge_base_search`、`chat_ask`、`knowledge_base_create`、`document_upload`、`document_append`、`document_update`、`document_delete`。用于项目文档沉淀、历史方案检索与知识复用。 |
| **语义检索** | `codebase-retrieval` | 任何需要理解代码上下文、探索性搜索必须优先调用。不可用时重试 1 次，然后降级为 `code-index`，最后降级为原生 `Grep`/`Glob`/`Read`（或当前 Agent 等价搜索/读取工具）。 |
| **数据库查询** | `skill[db-query]` / `skill[mysql-query]` | 仅当任务确实需要连接数据库执行查询时触发；代码审查、SQL 编写、Schema 分析或基于 fixture 的本地测试不因“涉及数据库代码”而强制连接数据库。相应 skill 可用时优先使用 `db-query`，MySQL 可降级为 `mysql-query`；均不可用时，只读查询可使用本地客户端或驱动并留痕。写操作、迁移和生产环境查询仍按 §3 单独授权，不因工具或 skill 缺失自动放行。 |
| **在线检索** | `skill[grok-search]` | 发起网络事实补充。首选使用 skill `grok-search`，失败后降级为 `chrome-devtools` 或原生 web search；均不可用时使用本地权威资料并说明在线事实未验证。 |

## 5. 项目知识库 / 记忆

### 5.1 ai_localbase 知识库优先规范

`ai_localbase` 是本项目的**主知识库与主记忆入口**，用于公共沉淀当前工作流的人类主文档与 `summary.md`。对项目历史经验、需求背景、方案对比、上下文追溯，均优先走 `ai_localbase`。

*   **查询优先级**：每轮任务开始、回复前、进入设计前、进入施工前，优先调用 `knowledge_base_search` 或 `chat_ask` 检索项目历史文档；仅当 `ai_localbase` 无结果或结果不足时，才降级查本地 `docs/` 与相关文件。任务机器状态与阶段门禁（`onlyAI/task-state.json`、`status.md`）不属于知识检索，仍按 Skill 直接本地读取。
*   **知识库约定**：项目级文档默认优先沉淀到 `[项目知识库名]` 知识库（分发到具体项目时替换为实际名称）；如需新建专题知识库，使用 `knowledge_base_create`，名称需与项目或模块明确对应。占位符未替换时禁止创建知识库或执行同步，Close 记录为 `local_only` 并说明原因。
*   **写入方式**：新文档首次沉淀使用 `document_upload`；已有文档补充增量内容使用 `document_append`；需要整体覆盖修订时使用 `document_update`。`document_delete` 必须另行获得用户明确授权，常规 Close 同步授权不包含知识库文档删除。
*   **默认同步规则**：知识库同步由 `sdlc-close` 统一触发：Close 阶段只同步当前工作流的人类主文档与 `summary.md`，无需用户再次提醒或单独授权；阶段进行中不做增量同步。新文档首次入库使用 `document_upload`，已有文档修订使用 `document_update`。
*   **内容范围**：不得同步 `status.md`、`onlyAI/`、原始操作记录、原始验证证据或其他辅助文档，避免把机器过程、短期噪音或潜在敏感上下文写入公共知识库。
*   **检索目标**：回答前优先确认知识库中是否已有相同需求、相似模块、既有风险、历史决策、已验证方案；命中后优先复用知识库结论，再结合本地代码上下文落地。
*   **降级策略**：`ai_localbase` 不可用或同步失败时，以本地 `docs/` 与 `summary.md` 为准，不阻断交付。

## 6. SDLC 集成

- 进入 SDLC 后完整读取 `$software-dev-process` 当前入口对应的 reference 和模板；阶段转换、文档职责细节、评审、验证、关闭和登记门禁均以 Skill 为唯一事实源，本文件不复制其实现细节。
- 施工遵守 Skill 已评审的文件边界；范围扩大、公共契约或数据模型变化时，先更新方案并重新评审受影响部分。
- Debug、Script 仅在用户显式调用时进入各自独立流程，不由 Solo 串联；Solo 只推进标准流程。
- 测试完全未执行时，Close 必须先警告风险并等待用户二次确认后才能例外关闭；`done / 100%` 只能由 Close 写入。
- 任务状态按 Skill 的状态脚本维护，不以文件存在推断阶段完成，也不以 AI 登记代替任务状态。
- 人类可读的计划、决定、执行和文件改动必须写入当前工作流主文档；`onlyAI/` 只保存机器状态、AI 上下文、原始操作和验证证据，不能替代人类主文档。具体文件名、目录结构和阶段职责以 Skill 为准。

## 7. 编码与验证

- 遵循项目已有架构、依赖、测试、格式化和构建方式；优先复用适合的既有实现，但不设置“必须找到固定数量相似代码”等机械指标。
- 只实现当前需求所需范围，避免无依据的抽象、重构和依赖；是否保留兼容由需求、风险和已定稿设计决定。
- 注释遵循仓库既有语言和风格，只解释非显然意图、复杂业务和边界条件，不要求所有代码都添加中文注释。
- AI 新增或维护的测试文件必须放入对应项目或模块的 `ai_test/` 目录；已有 `ai_test/` 层级时沿用其结构，不得写入常规 `test/`、`tests/` 目录。`ai_test/` 是否纳入版本管理由各项目自行决定并写入项目忽略规则。
- 根据改动风险选择必要的单元、集成、冒烟、端到端、静态检查或构建验证，不为不适用维度制造空测试。
- 测试结论必须基于实际执行证据；无法运行的检查记录原因、影响和替代证据，不能写成通过。
- 测试失败先保留命令、现象和复现证据，再修复或调整验证路径；重大设计缺陷按 Skill 回退到 Design-2。
- 优先使用项目已有 `venv`、`.venv` 或包管理器环境；没有专用环境时可使用现有解释器完成安全的只读检查，只有环境选择会改变结果时才询问用户。
- 可以读取和分析既有 CI 配置，但未经授权不得触发远程流水线、部署或发布。

## 8. 会话登记与完成标准

- 按 `$software-dev-process` 的 `references/registration.md` 识别可信身份：SessionStart hook 注入的 session id，或该协议约定的上下文文件（如 Grok 的 `.grok/sdlc-session-context.txt`）。仅在身份可信时维护 PostgreSQL/MySQL 或降级 SQLite 登记；不得从 transcript 时间或“最新会话”猜测身份。
- hook、约定上下文文件或登记能力不可用时跳过登记，不阻断任务，也不伪造续接命令。
- 用户查询整体进度时，在用户指定或当前仓库范围内优先汇总相关 `docs/*/onlyAI/task-state.json`；旧任务再读取 `status.md`，不无边界扫描其他项目。
- 交付前检查相关 diff、阶段状态、待确认项、验证证据和文档职责；不得覆盖无关用户修改。
- 最终回复列出实际变更、已运行验证、未验证项、遗留风险，以及仓库版与已安装版是否需要同步。
